Case study: How I use Claude and GitHub to keep improving my own website

This portfolio and halvia.cloud are kept up to date with Claude Code working in my GitHub repositories. Here’s the setup, the loop it runs, and where I stay in charge.

The problemThe setupThe loopHuman in the loopWhat it’s producedWhat I learnedFor other teams

01 · The problem

A site that keeps improving, without my evenings

A portfolio and a product site are never finished. There’s always a tile that’s out of date, a link that’s broken or a section that needs cutting back. Doing all of that by hand would take most of my evenings, and the small fixes would keep slipping.

02 · The setup

Claude Code, connected to my GitHub repos

  • Connected: Claude Code works directly in the GitHub repositories for this portfolio and for halvia.cloud.
  • On a branch: work happens on a branch, never on the live site.
  • Back as a pull request: changes come back to me as a pull request with a summary of what changed and why.
  • A rules file: a project rules file, CLAUDE.md, tells Claude the house style, what it must not touch, and how to check its work before handing it back.

03 · The loop

Goal in, pull request out

  1. I give a goal, such as “make every project tile consistent”.
  2. Claude makes the changes on a branch.
  3. It runs checks: broken links, layout on mobile and desktop, and accessibility.
  4. It fixes anything the checks find, and checks again.
  5. It opens a pull request with a summary.
  6. I review it, then merge or send it back.

04 · Human in the loop

I stay in charge of what goes live

  • Nothing goes live without my review. The sites only change when I merge.
  • The rules file lists what Claude must leave alone, such as the portfolio address on my CV.
  • Every change is visible in the GitHub history, so anything can be traced or rolled back.

05 · What it’s produced

Real changes on this site and Halvia

  • Halvia simplified: six sections removed, boxes squared, and the tools cut from seven to five admin tools, with a work log of everything checked. halvia.cloud
  • Halvia Ward rebuilt around the five tools, on the same blue as the main site. Try it
  • Side projects moved out: two personal projects moved to their own repository with their data and scheduled jobs, and the old links redirected.
  • This portfolio: consistent project tiles, a CV link, and this case study.

06 · What I learned

What went wrong early, and what fixed it

  • Scope has to be explicit. Early on, a request to change one thing could pull in neighbouring changes. Now each brief says what’s in, and “nothing else should change” when it matters.
  • Exclusions beat assumptions. Listing what not to touch, like the address on my CV, stopped surprises.
  • Checklists catch the boring failures. The checks found things I’d have missed, like a link to a section that no longer existed.
  • Automation needs watching. A scheduled job looked fine but was being skipped at busy times. Moving it off the quarter-hour fixed it.
  • AI output needs testing too. When I tested a small model for Halvia bot, it got a dose wrong. Tighter instructions and showing the source’s exact words fixed it.

07 · For other teams

The same loop, for your work

The loop works anywhere work lives in files: documentation that needs keeping current, weekly reports, internal tools, and content updates on a website. The goal changes; the branch, the checks, the pull request and the human review stay the same.

How I think about agents

Small jobs, clear rules, a person at the end

  • One job at a time. A focused task with a clear finish line is easier to check than a vague one.
  • One thread per task. Separate conversations keep the context short and on topic.
  • Memory on purpose. The rules file and pull request summaries carry what matters from one session to the next.
